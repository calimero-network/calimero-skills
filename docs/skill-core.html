Core Skill

How Calimero 1.0 works: one Raft log per app instance, a system group for who may do what, and a sealed channel to attested nodes

What This Skill Covers

The calimero-core skill gives your AI assistant the model behind every Calimero command and API: what an app instance is, how a call is run once and replicated, how organizations and access work, and what a client verifies before it sends anything. It teaches core 1.0 (1.0.0-rc.29); the 0.x model of contexts, gossip and CRDT merging is gone.

Covered Topics

  • App instances (v1's contexts), each with its own Raft log
  • The system group: nodes, accounts, organizations, packages, the app directory
  • Organizations, teams, roles, capabilities, access rules, invites
  • Accounts, passkeys, sessions, API keys, step-ups, the operator
  • Attestation, the sealed channel, receipts, packages and signers

The Life of a Call

# the client verifies the node, then seals every request to it
GET /attestation?nonce=… # quote checked against a signed mero-tee release
POST /apps/{app}/intents # sealed; any node forwards it to the app's leader

# the leader runs the component once and appends { call, outcome { result, diff, events } }
# a majority acknowledges; every replica applies the same diff

# the answer: { index, result, events, receipt }, the receipt signed by an attested key
POST /apps/{app}/views # a read, no log entry
GET /apps/{app}/events?from=N # committed events, then live (SSE)

Key Rules

Leader runs, followers apply
No gossip, no CRDT merging, no context sync: calls are linearized, state is plain collections (Text is the one CRDT left).
Package ≠ instance
A package (meroctl app) is signed code; an instance (meroctl instance) is one running copy with its own log, state, owner, organization and access.
Access
Every instance is in one organization, with an access rule: owner, accounts, org, team or public. A caller who does not reach it gets 404.
Credentials
People sign in with passkeys (15-minute sessions); machines use scoped API keys (cal_…). Sensitive actions need a passkey step-up (412 CONFIRM_REQUIRED).
